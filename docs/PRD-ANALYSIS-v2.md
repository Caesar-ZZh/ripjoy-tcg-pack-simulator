# RipJoy PRD 全面剖析与 v2 规划

> 剖析对象：`docs/PRD.md` v1.0（2026-10-27）与已上线产品（2026-10-29，28 弹 / 5,767 张卡）
> 剖析目的：为集换社产品经理岗投递做准备——把 RipJoy 从「开包模拟器」升级为能证明**数据驱动、AI 独立交付、TCG 行业认知**三项 JD 核心要求的作品
> 结论先行：v1 PRD 的产品内核（真实优先、演出分级、手机优先）全部成立且已超额交付；但**文档与产品已严重漂移**，且 v1 定位与集换社业务（行情 / 交易 / 评级）之间缺一层连接。v2 的任务不是重做开包，而是补上 A 行情估值、B 官方口径两个 P0 模块，并给 C 战报、D 卡鉴留独立入口。

---

## 1. v1 PRD 逐节剖析（文档 vs 现实）

| 章节 | v1 写了什么 | 实际交付（10-29） | 漂移 / 问题 |
|---|---|---|---|
| §1 背景与机会 | 集换社等平台证明用户对卡价/出率敏感；差异化 = 只把开一包做到极致 | 定位成立，用户反馈五轮均围绕「真实感」（卡图清晰度、卡背、张数、官方规格） | 机会判断被验证；但「与集换社的关系」只停留在一句背景，没有落成功能——v2 的 A/D 正是补这一层 |
| §2 目标用户 | 玩家 / 主播 / 泛粉丝三类 | 未做主播向功能（录屏模式、竖屏安全区外无特别支持） | 主播场景是纸面人群，v2 不投入，但在 Case Study 中应主动说明取舍 |
| §3 产品原则 | 真实优先、演出分级、手机优先、零门槛、克制变现 | 五条全部兑现，且「真实优先」被用户反复加码（真实包装图、真实卡背、逐弹张数、官方概率） | 原则是本项目最强的资产，v2 只追加一条：**数据口径分级标注**（官方 / 社区 / 暂无，永不混淆） |
| §4 弹系与卡池 | 4 弹（EN 151 / Surging Sparks / Destined Rivals / 日版 151） | 28 弹、四语言、5,767 张；每包张数已逐弹按实物核正（太晶盛聚 10 张为唯一修正项） | 章节整体过时，需按现状重写；「运行时拉取模式」的 v1.5 设想已被静态分片方案取代（更稳） |
| §5 概率模型 | EN 卡槽模型 + 社区校准；v2 预告「真实模式」开关 | 社区模型已公示；真实模式未做 | **新证据改变了最优解**：简中官方公布了每包构成与生产配比（见 §4 模块 B），简中五弹应直接换官方口径，比「真实模式开关」更可信、更有行业含金量；EN/JA 维持社区模型并明确标注 |
| §6 核心流程与演出 | CSS 绘制卡包、撕口动画、漏光、L0–L4 矩阵 | 全部实现且多次升级：真实包装图（57 张）、真实卡背（国际版/日版）、六类新粒子、十连逐包流 | §6.1「CSS 绘制包装」已被真实包装图取代——这是用户驱动的正确漂移，文档需回写 |
| §7 功能清单 | P0 九项；P1 含分享卡；P2 含「与集换社价格对照」 | P0 全清；图鉴墙、语言筛选为计划外新增；P1 分享卡未做（= 模块 C）；P2 价格对照未做（= 模块 A 的前身） | v1 自己埋的两个钩子（分享卡、价格对照）恰好是 v2 的 C 与 A，叙事连贯 |
| §8 视觉设计 | 深空藏青、克制、演出时华丽 | 兑现；另加舞台氛围光随弹主题色 | 无漂移 |
| §9 技术方案 | 零构建静态站；「数据 JSON 合计 <600KB gzip」 | 架构未变；但简中数据已达 83MB 本地 / 线上 27 个分片按需加载，EN/JA/TW 走 CDN 图 | 性能章节失效需重写：现状是「元数据轻量 + 简中分片懒加载 + 图片 CDN/内嵌混合」，并有实测加载数据（首开一弹约 15–21MB、缓存后秒开） |
| §10 验收标准 | 2026-10-28 的五条 | 已全部通过且被后续五轮迭代覆盖 | 需为 v2 各模块另立验收（见 §7） |
| §11 风险 | 「不打包分发卡图（全部走 CDN 引用）」 | **与现实不符**：简中五弹卡图以 data URI 内嵌在数据文件里分发（因无可用 CDN） | 合规口径必须修正为实话：粉丝非商业作品、卡图来自公开百科/图库、权利归版权方、提供下架通道；面试被问到时按修正口径答 |

**剖析小结**：v1 PRD 作为「一天交付」的文档质量很高，问题不在写错，而在产品跑得比文档快。投递前必须做一次文档回写（PRD v1.1），否则面试官对照仓库会发现三处硬伤：弹系表过时、性能数字假、版权口径与代码不一致。

## 2. 与集换社 JD 的差距映射

| JD 要求 | 已有证据 | 缺口 | v2 对应 |
|---|---|---|---|
| 数据驱动迭代 | 五轮用户反馈闭环；概率公示；逐弹规格审计 | 没有「价值/行情」维度的数据产品；没有埋点与指标意识的展示 | A 行情估值（EV、回本率、资产盘）+ Case Study 中补指标框架 |
| 独立用 AI 搭完整产品 demo | 28 弹全栈静态站、三天多轮上线验活 | 演示叙事散在提交记录里，未成文 | Case Study 文档（收口动作，非功能） |
| TCG 认知优先 | 真实卡池、稀有度体系、官方张数核正 | 概率仍是社区口径；不懂「封入率官方表」这层行业知识的印象 | B 简中官方口径——直接采用官方构成与生产配比，行业含金量最高的一项 |

## 3. v2 总体方案

**定位升级**：从「开包模拟器」到「开包 + 行情 + 识卡的 TCG 玩家工具」——开包是流量与爽点，行情是集换社的语言，卡鉴是业务的想象空间。

**信息架构**（底部/顶部导航五视图，C 为场景入口不占导航）：

```
选弹（现有） → 开包 → 结算 ──→ [C 战报：生成分享图]
行情（A，新增）   资产总览 / 单弹期望值榜 / 收藏估值走势
卡鉴（D，新增）   选卡估价 / 评级预检
收藏（现有）      增：总估值、估值快照
战绩（现有）      概率公示（双口径）、历史（增：每条可生成战报）
```

**排期**（投递截止 10-31）：
- P0（10-29 ~ 10-30）：模块 B 引擎与数据、模块 A 行情页
- P1（10-30 ~ 10-31）：模块 C 战报、模块 D 卡鉴 v1
- 收口（10-31）：PRD 回写 v1.1、README 更新、Case Study、简历链接验活

## 4. 模块 B：简中弹官方封入率（P0）

### 4.1 已核实的官方事实（来源：pokemon.cn 商品规格、52poke 各弹「规格」表）

| 弹 | 采用版本 | 官方构成 | 备注 |
|---|---|---|---|
| 太晶盛聚 CSV9.5C | 10 张装（唯一版本，¥30） | 7 张平卡 + 3 张闪卡，或 6 平 + 4 闪 | 平卡 = C/U/R；闪卡含 RR、精灵球/大师球纹样、ACE、SAR、SR、UR |
| 星彩晶璃 CSV9C | 5 张装（另有 20 张装，按既定规则取 5） | 4 张平卡 + 1 张闪卡 | 官方概率表含每档种类数与生产配比 |
| 璀璨诡幻 CSV8C | 5 张装（同上） | 4 平 + 1 闪 | 闪卡位生产配比分组：约 80% 平闪侧…（以抓取的官方表为准） |
| 利刃猛醒 CSV7C | 5 张装（同上） | 4 平 + 1 闪 | 同上 |
| 收集啦151 151C | 5 张装（另有 20 张装） | 4 平 + 1 闪（以官方表为准） | 四个子弹合并为一弹，官方表按子弹发布，合并口径需在公示页注明近似 |

### 4.2 引擎改造

- 引入**卡槽规格驱动**：数据文件新增 `spec` 字段（槽位数组：每槽 = 张数 + 候选档位池 + 权重表），`openPack` 优先读 `spec`，无 `spec` 时回落现有按张数分支（EN/JA/TW 不动）。
- 平卡槽：在 C/U/R 池内按官方种类数比例抽（非闪版面）；闪卡槽：按官方生产配比先 roll 档位组、再组内 roll 具体档位、最后在该档位池内等概率抽卡（球纹变体在数据层与同编号普通版同名不同图，按现有 `rk`/变体处理对齐）。
- 太晶 10 张：双构成随机（7+3 与 6+4 的比例官方未公布，按 50/50 并在公示页标注为假设）。
- 首包保底与 `spec` 的交互：保底改为「闪卡槽强制 AR 以上档位组」，保持一次性逻辑不变。

### 4.3 数据任务

- 抓取 52poke 五弹规格表 → 转成 `spec` JSON（脚本 `scripts/build-cn-spec.py`，原始表截图/文本存 `docs/` 备查）。
- 校验：每弹模拟 100,000 包，档位分布与官方表逐项对照，偏差 >1.5pct 的档位回查权重转录。

### 4.4 展示

- 战绩页概率公示拆两栏：「官方口径（简中五弹）」与「社区校准（EN/JA/TW）」，各自标来源与日期。
- 弹卡与开包页对简中弹加「官方封入率」角标——小改动、强信号。

## 5. 模块 A：行情与估值（P0）

### 5.1 数据现状（决定功能边界）

| 数据 | 覆盖 | 用途 |
|---|---|---|
| 单卡参考价 `p`（Cardmarket 趋势价，EUR） | EN 19 弹 ~100%；繁中 2 弹 ~100%；日版 151 ~100%、热风 6/92；简中 0% | EV 与估值只对覆盖率达标弹开放（门槛：张数覆盖 ≥90% 且高档位全覆盖） |
| 包价 | 无现成数据 | 每弹设「参考包价」常量（EN €6 / 日版 ¥200 折算等，逐弹查证后写表），页面明示可改，EV 随之重算 |

### 5.2 功能点

1. **资产卡（首页顶部 + 收藏页）**：收藏总估值（€）、藏品数、近 7 次打开的估值快照迷你走势（快照存 localStorage，首次使用从今天起积累——不伪造历史）。
2. **单弹期望值面板（行情页）**：每弹一行：每包期望卡值（Monte Carlo 模拟 5,000 包，打开面板时现场算，池已在内存、毫秒级）、中位数、回本概率 P（单包总值 ≥ 包价）、SAR 期望包数 1/p、出 SAR 概率曲线（开 X 包至少一张的概率，X=10/30/50/100）。简中弹显示「暂无行情数据」并给一句业务注脚（价格数据需平台方授权——面试钩子）。
3. **弹卡 EV 徽标**：选弹页每张弹卡右下角小字「期望 €X.X / 包」，帮用户「用钱投票选弹」——与集换社查价心智一致。
4. **结算页增补**：本包总值旁加「本包回报率 = 总值 / 包价」，与 C 战报共用。

### 5.3 验收

- 任选一弹，面板 EV 与独立脚本模拟（同种子 100k 包）偏差 <3%。
- 无价格弹不出现 €0.00 或假数字（防 §5.2 旧坑复发）。

## 6. 模块 C：开包战报分享图（P1，独立入口）

- **入口**：结算页主按钮区「生成战报」；历史列表每条的次级按钮。两个入口共用同一生成器。
- **内容**（1080×1440 竖版海报）：最佳卡大图、弹名与日期、本包总值与回报率（A 的数据）、稀有度分布小条、一句随机文案、RipJoy 标识与站点短链。
- **实现**：Canvas 离屏绘制，卡图跨域走现有 data/CDN 图源（简中为 data URI、英文为 CDN high 图，需 `crossOrigin` 失败时降级为无图版海报）；产物为 PNG 下载 + 移动端长按保存提示。
- **验收**：中英各一弹生成成功、图内数字与结算页一致、弱网下不白屏（降级版）。

## 7. 模块 D：卡鉴（P1，独立入口）

- **定位**：评级预检 + 估价的概念演示，对应集换社的评级/查价业务；顶部导航独立 tab「卡鉴」。
- **v1 范围（全部客户端可实现，不造假 AI）**：
  1. 选卡：按弹 → 按编号/名称选卡（复用已加载卡池，未加载弹按需 `loadSet`），或从收藏里直接选。
  2. 估价卡：卡面大图、参考价（有价弹）、该卡在弹内的价格分位（「比本弹 87% 的卡贵」——数据现成、很集换社）。
  3. 评级预检：四维互动打分（居中：拖动对齐框模拟；边角/边缘/表面：对照示例图自评滑杆）→ 加权预检分 → 预估评级区间（如「9–10 区间」）+ 每维改进提示 + 「正式评级请走集换社送评」业务注脚。
- **明确不做**：拍照自动识卡（客户端无可靠方案，假识别会砸可信度）；面试话术 = 「v2 接平台图像识别 API 的方案设计」（Case Study 里写方案，不写已实现）。
- **验收**：任意弹任意卡可走通三步；无价卡（简中）显示估价缺失态而非假价；预检分随滑杆实时变化且区间映射稳定。

## 9. 风险与取舍

| 风险 | 应对 |
|---|---|
| 官方表转录错误（B 的命门） | 双人校验法：脚本抓表 + 模拟分布反验；公示页附原表链接 |
| 包价假设被质疑（A） | 全站统一标注「参考包价，可改」，EV 公式与模拟次数公示——把假设做成透明反而是加分项 |
| 两天工期溢出 | P0/P1 分级已定：A/B 必须完，C 可砍到只保留结算页入口，D 可砍到只做「选卡估价」半步 |
| 简中无价导致 A 在主打弹上缺席 | 不掩盖：行情页把简中弹列为「待接入数据源」，与 D 的业务注脚一起构成「为什么需要集换社」叙事 |
