# Case Study：开包有喜 RipJoy —— 从「开包模拟器」到「有行情、有官方口径的 TCG 工具」

> 作者：朱子浩（产品 + AI 协作独立开发）｜周期：2026-10-27 v1 上线，10-29 完成 v2｜在线体验：https://caesar-zzh.github.io/ripjoy-tcg-pack-simulator/
> 配套文档：产品文档 `docs/PRD.md`（v1.1）、全面剖析与 v2 规划 `docs/PRD-ANALYSIS-v2.md`、官方规格表存档 `docs/official-tables/`

## 一句话

一个手机端的宝可梦 TCG 开包模拟器：28 弹、5,767 张真实卡、简中五弹按官方封入率模拟、22 弹可算每包期望值——我用它验证一件事：**TCG 玩家对模拟器的信任，来自数据口径的可验证，而不是演出有多华丽。**

## 问题：玩家不信模拟器的三个地方

调研同类产品（PokéRip 等）与玩家社区后，差评集中在三点：卡池是假的或过时的、概率是黑箱（想让你上头就暗调）、开出来的卡「不值钱」——没有价格参照，爽感无法换算。v1 先解决前两点的一半：真实卡池（TCGdex 全量数据）+ 社区校准概率公示 + 分稀有度演出。v1 上线后我对着 PRD 做了一次全面剖析，结论是：产品内核成立，但与真实 TCG 业务（行情、评级）之间缺一层连接——这正是 v2 的命题。

## 五个关键决策（每条含取舍与验证）

**1. 真实感优先级高于功能数量。**
卡图从低清 CDN 图一路升级到：英文/日文 600px 源图、简中弹自建高清管线（百科扫描 + 图库对齐修复）、真实包装图（57 张官方包装）、真实卡背（国际版/日版两种）。取舍：数据工程吃掉大半工时，功能清单因此克制。验证：用户（我自己就是重度 TCG 用户，另有大阪 oripa 期望值测算的习惯）五轮反馈全部围绕真实感细节，说明方向对。

**2. 规格不按「默认值」，按 SKU 证据逐弹审计。**
起因是我自己发现太晶盛聚包装上印着「10 张」而产品里是 5 张。于是把 28 弹的每包张数全部按证据重核：包装印刷字样、pokemon.cn 商品规格、52poke 数据交叉验证；同一弹有多种装数时按最小标准装（简中 5 张装优先于 20 张装）。结果：27 弹原本正确，太晶盛聚 5→10 为唯一修正。方法论沉淀为一条产品原则：**弹系规格是 SKU 级事实，不是语言级默认值。**

**3. 概率口径：能拿到官方数据时，就不要用社区模型凑数。**
原计划给英文弹做「真实模式」开关（把 SAR 概率调回真实量级）。查规格时发现：简中官方完整公布了每包构成与各档位生产配比——于是砍掉开关，改为**卡槽规格驱动引擎**（`spec`：平卡槽 + 闪卡槽、组内按种类数抽取），简中五弹直接按官方口径模拟；精灵球/大师球纹样这类数据集里没有独立条目的印刷变体，用「同卡 + 闪卡工艺标记」诚实近似并公示。验证：每弹 100,000 包模拟，档位组分布与官方条件分布偏差 ≤0.1 个百分点；官方未公布的两处（太晶双构成比例、收集啦151 四子弹合并）以假设形式写进公示页。

**4. 行情层：数据不够格，就明说不算。**
行情页对每弹做 4,000 包 Monte Carlo：期望卡值、中位值、回本概率、出 SAR/金卡的期望包数。但先立门槛：价格覆盖 ≥90% 且高档卡全部有价才准计算——英文 19 弹、日版 151、繁中 2 弹达标（共 22 弹）；简中五弹与日版热风（6/92 有价）直接显示「暂无行情数据」。参考包价做成可改输入并公示假设（EN €5.49 等），回本率随改即时重算——**把假设透明化，而不是藏进数字里**。实测样例：Surging Sparks 期望 €8.18/包、回本概率 34%、约 23 包出一张 SAR/金卡（单次模拟值）。

**5. 两个业务入口，各占一个位置，不混进开包主流程。**
战报（结算页 + 历史双入口）解决「开完想晒」：Canvas 生成竖版海报（最佳卡、总值、回报率），对应内容传播；卡鉴（顶部独立入口）解决「这张卡怎么样」：选卡看本弹价格分位 + 四维评级预检（居中/边角/边缘/表面加权出预估区间）。明确不做拍照自动识卡——客户端没有可靠方案，假识别会砸掉前四条决策攒下的全部信任；识卡的方案设计留在规划里，等平台级识别 API。

## 结果数字

| 项 | 数 |
|---|---|
| 弹系 / 卡数 / 语言 | 28 弹 / 5,767 张 / 简·英·日·繁 |
| 官方口径弹 | 简中 5 弹（模拟 vs 官方分布偏差 ≤0.1pct） |
| 行情可算弹 | 22 弹（4,000 包/弹 Monte Carlo） |
| 迭代闭环 | v1 上线后 7+ 轮「反馈→修复→双端验活」，含 2 次验活抓到的真 bug（见下） |
| 性能取舍 | 简中全高清首开约 15–21MB（分片懒加载，缓存后秒开）——用加载成本换卡面真实感，明示于 PRD |

## 两个被验活抓到的真 bug（质量意识）

- **iOS Safari 翻卡后仍显示背面**：卡背用 `<img>` 元素时 iOS 的 backface-visibility 失效；桌面浏览器验活全过、真机才暴露。改为背景图渲染 + 翻面中途切可见性类后修复。教训已沉淀为检查清单：动效类改动必须在 iOS 路径验活，桌面通过不算完成。
- **历史战报按钮点击无反应**：绑定代码写在页面初始化时执行，那时列表为空。改事件委托后修复。教训：动态列表的事件绑定一律用委托。

## 如果这个产品由集换社来做

三件我做不了、平台能做的事，恰好是这个 demo 指向的路线：① 简中卡价格数据接入（行情页最大的缺口立刻补齐，EV 榜就是现成的查价入口）；② 拍照识卡 API（卡鉴的选卡环节换成拍照，预检和估价分位已经就位）；③ 评级服务打通（预检区间 → 一键送评，是完整的转化漏斗）。这个作品想证明的是：我能独立把一个 TCG 产品从数据、口径、体验做到可上线，并且对「哪些数据能用、哪些不能装」有职业级的诚实。
